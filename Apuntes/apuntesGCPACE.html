Jerarquía de Recursos

Google Cloud organiza los recursos de forma jerárquica para facilitar la gestión centralizada, la herencia de políticas de seguridad (IAM) y el control granular de costes. Esta estructura es similar a un árbol donde las políticas fluyen desde la raíz hasta las hojas.

La Estructura Detallada

1

Organización (Nodo Raíz)

Representa a toda tu empresa. Es donde se definen las políticas globales y se tiene visibilidad de todos los recursos. Requiere un dominio de Google Workspace o Cloud Identity.

2

Carpetas (Folders)

Agrupación lógica para organizar proyectos por departamentos (Ej: Ventas, IT) o entornos (Ej: Prod, Dev). Permiten delegar la administración de forma segmentada.

3

Proyectos (Unidad de Servicio)

Es la base para usar cualquier servicio. Aquí se habilitan las APIs, se asocia una cuenta de facturación y se gestionan los recursos individuales.

Reglas Clave de Examen 🚨

  • Facturación (Billing): Se configura a nivel de Proyecto. Un proyecto solo puede tener una cuenta de facturación activa, pero una cuenta de facturación puede pagar muchos proyectos.
  • Herencia de Permisos: Las políticas IAM fluyen hacia abajo. Si eres "Viewer" en una Folder, eres "Viewer" en todos sus proyectos. No se pueden quitar permisos heredados, solo añadir más.

Identidad y Accesos (IAM)

🔥 El Principio de Mínimo Privilegio (Least Privilege)

Este es el concepto de seguridad más importante en GCP. Significa que cada usuario, grupo o aplicación debe tener exactamente los permisos que necesita para hacer su trabajo, y nada más. Esto reduce el "radio de explosión" en caso de una brecha de seguridad.

Roles Básicos

Owner, Editor, Viewer. Son "Legacy" y demasiado potentes.

⚠️ Evitar en producción
Roles Predefinidos

Storage Admin, Instance Admin. Creados por Google para tareas específicas.

✅ Recomendado Examen
Roles Personalizados

Tú eliges los permisos uno a uno. Mayor control.

🛠️ Para control granular

🤖 Cuentas de Servicio (Service Accounts)

Son identidades especiales para recursos y aplicaciones (no para humanos). Permiten que una VM o una Cloud Function acceda a otros servicios de forma segura.

Service Account User

Es el rol que necesita un desarrollador para "adjuntar" una Service Account a una VM. ¡Sin este rol no puede crear la VM con esa identidad!

Scopes vs IAM

Los Scopes son el método antiguo. La recomendación es usar "Allow full access to all Cloud APIs" y luego restringir de verdad usando Roles IAM en la Service Account.

� Gestión de Grupos

SIEMPRE asigna roles a Grupos de Google, nunca a emails individuales.

¿Por qué? Porque si alguien deja la empresa, solo lo quitas del grupo y pierde todos los accesos de golpe. Si lo hicieras individual, tendrías que ir proyecto por proyecto limpiando.

OS Login

Es la forma moderna y segura de entrar por SSH a tus VMs. Vincula tu cuenta de Google con el sistema operativo de la VM.

🎯 "Pregunta de SSH seguro" → Respuesta: OS Login + IAM Roles (osLogin / osAdminLogin).

# Añadir una política IAM via CLI gcloud projects add-iam-policy-binding [PROJECT_ID] \ --member="group:admins@miempresa.com" \ --role="roles/compute.admin"

SERVERLESS (Apps)

Managed Instance Groups (MIG)

Un MIG es un grupo de VMs idénticas creadas a partir de una Instance Template. Son la base de la alta disponibilidad en GCP.

Autohealing

Si una VM falla o su aplicación deja de responder (según un Health Check), el MIG la borra y crea una nueva automáticamente.

Autoscaling

Añade o quita VMs según la carga (CPU, tráfico del LB, o métricas personalizadas). 🎯 Clave: "Ahorro de costes + Rendimiento".

Preemptible & Spot VMs

Son VMs con un descuento masivo (hasta 80%), pero con una condición: Google puede apagarlas en cualquier momento si necesita capacidad para otros clientes.

🚨 Reglas de Oro Examen:
  • Duran un máximo de 24 horas.
  • Ideales para Batch Jobs, renderizado, o cualquier tarea que pueda reanudarse si se interrumpe.
  • NUNCA para bases de datos o servidores web críticos.

Almacenamiento y Datos

🧠 Cloud Storage: Clases y Estrategia

Cloud Storage es un servicio de almacenamiento de objetos (archivos). El examen se enfoca en elegir la clase de almacenamiento correcta para minimizar costes según la frecuencia de acceso.

Clase Frecuencia / Caso
Standard Acceso diario (Web, Apps).
Nearline Acceso < 1 vez al mes.
Coldline Acceso < 1 vez al trimestre.
Archive Acceso < 1 vez al año (Backups).
Lógica de Costes

A medida que bajas de Standard a Archive:

  • Baja el coste de almacenar el GB.
  • Sube el coste de acceder/leer los datos.

Tip Examen 🎯

"Guardar backups por 7 años por cumplimiento" → Archive.

⚙️ Lifecycle Management (Ciclo de Vida)

Permite automatizar acciones sobre tus objetos basándose en condiciones (como la edad del archivo o el número de versiones).

SetStorageClass

Mueve archivos de Standard a Coldline automáticamente después de 30 días.

Delete

Borra logs o versiones antiguas después de 1 año para ahorrar espacio.

VPC y Redes

🧠 Conceptos Clave de Red

A diferencia de otras nubes, la VPC de Google es Global. Esto significa que puedes tener una red que abarque todo el mundo sin necesidad de túneles complejos.

  • VPC Global / Subnets Regionales

    La red es global, pero cada subred vive en una región específica (Ej: us-central1).

  • Firewall Stateful

    Si permites el tráfico de entrada (Ingress), la respuesta de salida (Egress) se permite automáticamente. 🎯 Tip: Las prioridades bajas (ej: 100) se ejecutan antes que las altas.

Conectividad con el Mundo Real

Cloud VPN

Conexión encriptada a través de la Internet pública. Rápida de configurar, pero depende de la calidad de Internet.

Dedicated Interconnect

Un cable físico directo entre tu oficina y Google. Máxima velocidad y seguridad, pero más caro y lento de instalar.

Cloud Router

Intercambia rutas dinámicamente usando el protocolo BGP. ¡Imprescindible para VPNs dinámicas!

Acceso Privado a Google

Escenario Típico: Tienes una VM sin IP pública por seguridad, pero necesita subir archivos a Cloud Storage o consultar BigQuery.

Solución de Examen 🎯

Private Google Access

Permite usar la IP interna de la VM para hablar con las APIs de Google.

Balanceadores (Load Balancers)

Global HTTP(S): Para tráfico web. Soporta IPv6 y WebSockets.
Regional Network: Capa 4 (TCP/UDP). Muy rápido, para apps no web.
Internal: Balanceo entre tus propios microservicios dentro de la VPC.

Cloud Operations

La suite de Cloud Operations (antes Stackdriver) es el centro de mando para observar la salud de tus aplicaciones. Se divide en tres pilares fundamentales que debes diferenciar en el examen.

Monitoring

"¿Cómo de rápido va mi app?"

Gestiona Métricas (CPU, Latencia, Uso de Disco). Permite crear Dashboards y Uptime Checks.

Logging

"¿Qué ha pasado exactamente?"

Almacena Eventos y mensajes de texto. Esencial para depurar errores y auditorías de seguridad.

Alerting

"¡Avísame si algo falla!"

Envía notificaciones cuando una métrica supera un umbral o un log específico aparece.

🧠 Auditoría de Logs (Cae mucho)

GCP genera logs de auditoría automáticamente. Debes saber qué tipo de información hay en cada uno para responder preguntas sobre "quién hizo qué".

Admin Activity Logs

Registran cambios en la configuración o metadatos de los recursos (Ej: alguien borró un disco). Siempre activos y gratuitos.

Data Access Logs 🔥

Registran quién ha leído o escrito dentro de los recursos (Ej: alguien leyó un archivo en un Bucket). Deben activarse manualmente (pueden generar costes).

Sinks: Exportación de Logs

Por defecto, los logs se borran después de 30-400 días (según el tipo). Si necesitas guardarlos más tiempo o analizarlos a fondo, usas un Sink:

BigQuery

Para análisis SQL masivo de tus logs.

Cloud Storage

Para cumplimiento legal a largo plazo (Barato).

Pub/Sub

Para enviar logs a una app externa en tiempo real (Ej: Splunk).

Despliegue e Infraestructura

🧠 Infraestructura como Código (IaC)

IaC permite definir tu red, tus VMs y tus bases de datos en un archivo de texto. Esto hace que tus despliegues sean repetibles, sin errores manuales y versionables en Git.

Deployment Manager

Es el servicio nativo de Google. Usas archivos YAML para describir tus recursos. Si la pregunta menciona "Templates" o "Config files" de Google, la respuesta suele ser esta.

Terraform

Es la herramienta estándar de la industria (no solo de Google). Muy potente para gestionar infraestructuras complejas y multi-nube.

CI/CD: Cloud Build

Cloud Build es el servicio que ejecuta tus pasos de construcción. Por ejemplo: descargar el código de Git, compilarlo, crear una imagen de Docker y subirla al Artifact Registry.

# cloudbuild.yaml
steps:
- name: 'gcr.io/cloud-builders/docker'
  args: ['build', '-t', 'mi-app', '.']

GKE (Kubernetes Engine)

🧠 ¿Qué es GKE?

Google Kubernetes Engine es un servicio gestionado para ejecutar aplicaciones en contenedores. GKE se encarga de la salud de los nodos, las actualizaciones y el escalado.

Autopilot (Recomendado)

Google gestiona toda la infraestructura, incluyendo los nodos. Tú solo pagas por los Pods que ejecutas. Es la opción con menos pasos operativos.

Standard

Tú tienes el control total de los nodos (VMs). Puedes elegir el tipo de máquina, gestionar tus propios pools de nodos y tienes más flexibilidad, pero más trabajo.

Relación entre Objetos

Pod

Unidad Mínima

Donde corre tu contenedor. Los Pods son efímeros (pueden morir y renacer).

Depl

Deployment

Dice cuántas copias (réplicas) de tu Pod deben estar corriendo.

Serv

Service

Da una IP estable para que los usuarios o apps puedan hablar con tus Pods.

Escalado en GKE (Diferencia clave)

HPA (Pod Autoscaler)

Crea más copias de tu app (Pods) si hay mucho tráfico.

Cluster Autoscaler

Crea más servidores (Nodos/VMs) si ya no caben más Pods en los actuales.
